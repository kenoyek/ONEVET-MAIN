# Reviewing changed booking requests — 18 November 2026

Booking response controls now pause after a request-version conflict, slot conflict or access-change error. The response explanation remains editable and retained, and an explicit Refresh request details action reloads the recorded state before another decision. If refreshing throws while the card remains available, it keeps the decision lock and explanation. Existing parent access/error states can hide the whole record; this does not add draft persistence across navigation or access loss. Provider confirmation, decline, cancellation, completion and rescheduling controls follow this review state; messages and recorded details remain accessible according to existing permissions.

The response call uses a synchronous lock, and a changed-request error sets a separate review guard before another submission can occur. A successful response is reported as saved even if the subsequent refresh fails, rather than incorrectly inviting the same decision to be sent again. Explanations clear only after an acknowledged write. Ordinary ambiguous network errors retain the existing expected-version retry behavior; backend concurrency and authorization remain authoritative.

The shared request card provides the same recovery for customer responses where applicable. A refresh does not confirm, cancel or otherwise mutate a booking. No new role permissions, RPCs, migrations, payments or cloud environment publication are introduced.
